# AI Mock Interviewer

AI Mock Interviewer is a full-stack adaptive technical interview platform. It lets a user start a timed coding interview, solve LeetCode-style questions in a browser editor, run code in a sandbox, submit an explanation, and receive score-based feedback from a deterministic evaluator plus an optional ML scoring service.

The current project version includes a curated question bank of 342 unique coding problems, a MongoDB-backed interview/session system, a Piston-powered execution pipeline, and a FastAPI ML microservice trained on rubric-aligned synthetic submission data.

## Architecture

```text

  React UI, Monaco editor, Redux state, API calls

  Express API, auth, interview sessions, adaptive selection,
  code execution wrapping, scoring, feedback, MongoDB models

ml_service/
  FastAPI scoring model service and training scripts

docker-compose.dev.yml
  MongoDB, Redis, Piston, ML service for local development
```

High-level request flow:

```text
User opens frontend
  -> Login/register through backend
  -> Start interview session
  -> Backend selects a question from MongoDB
  -> Frontend shows question, editor, examples, constraints
  -> User runs/submits code
  -> Backend wraps code with a test harness
  -> Piston executes the code
  -> Backend compares actual output with expected output
  -> Feature extractor builds scoring features
  -> Deterministic scorer computes baseline score
  -> ML service predicts/calibrates score
  -> Feedback engine creates final feedback
  -> Session and user skill profile are updated
```

## How the Interview Flow Works

### 1. Session Start

`client/src/pages/InterviewSetupPage.jsx` lets the user choose:

- language
- topics
- number of questions
- duration
- target difficulty, or automatic difficulty

The frontend calls:

```text
POST /api/v1/interviews/sessions
```

The backend creates an `InterviewSession`, calculates initial difficulty from the user's skill profile, and asks `adaptive.service.js` for the first question.

### 2. Adaptive Question Selection

`server/src/services/adaptive.service.js` uses a threshold-based adaptive algorithm:

- Initial difficulty is the average skill level for selected topics, defaulting to `3`.
- After each answer:
  - score `>= 70`: increase difficulty by `0.5`
  - score `< 40`: decrease difficulty by `0.5`
  - otherwise: keep difficulty similar
- If the last 3 answers average `>= 80`, add a small extra increase.
- If the last 3 answers average `< 30`, add a small extra decrease.
- Topic priority favors weaker topics and topics asked fewer times in the current session.
- Question selection first tries exact topic and difficulty, then broadens difficulty, then broadens topic.

Questions are excluded only within the current session. They can appear again in future sessions.

### 3. Code Execution

When the user runs or submits code, the backend calls `server/src/services/execution.service.js`.

The execution service:

1. Reads the question test cases.
2. Parses the user's function signature.
3. Wraps code with a language-specific test harness.
4. Sends the wrapped code to Piston.
5. Captures stdout, stderr, exit code, timeout, and runtime.
6. Normalizes output and compares it with expected output.

This is why correct code now receives high correctness even when the ML model is present: correctness comes primarily from real test execution, not from guessing.

### 4. Feature Extraction

`server/src/eval/featureExtractor.js` extracts code and explanation features:

- `testPassRate`
- `executionTime`
- `codeLength`
- `codeCharCount`
- `errorCount`
- `complexityScore`
- `implementationCompleteness`
- `passedTestCases`
- `totalTestCases`
- `hasMeaningfulCode`
- `hasExplanation`
- `explanationClarity`
- `reasoningDepth`
- `structuredThinking`
- `approachRelevance`
- `explanationCompleteness`
- `explanationWordCount`

Code features come from test results, line/character counts, simple syntax/loop analysis, and placeholder detection.

Explanation features come from keyword overlap with the expected approach, structure cues, complexity mentions, reasoning cues, and word count.

### 5. Deterministic Scoring

`server/src/eval/scoring.js` computes a deterministic baseline score.

Correctness dominates the score:

```text
If testPassRate == 100:
  code score = 100

If testPassRate >= 80:
  code score = test * 0.70 + quality * 0.25 + efficiency * 0.05

If testPassRate >= 60:
  code score = test * 0.75 + quality * 0.20 + efficiency * 0.05

If testPassRate < 60:
  code score = test * 0.80 + quality * 0.15 + efficiency * 0.05
```

Additional safeguards:

- no meaningful code gives `0`
- zero passing tests caps code score near the bottom
- perfect code-only submissions are forced to `100`
- if code and explanation are both present, the combined score is:

```text
overall = codeScore * 0.85 + explanationScore * 0.15
```

### 6. ML Score Calibration

`server/src/eval/mlClient.js` sends the extracted features to:

```text
POST http://localhost:8000/predict
```

The backend then blends deterministic and ML scores:

```text
final = deterministicOverall * 0.70 + mlPrediction * 0.30
```

The ML model calibrates scoring, but it does not override hard correctness guarantees. If all tests pass with meaningful code, the final score is at least `95`, and code-only perfect submissions become `100`.

### 7. Feedback Generation

`server/src/eval/feedbackEngine.js` generates user-facing feedback:

- correctness summary
- strengths
- weaknesses
- recommendations
- code quality notes
- runtime notes
- explanation quality notes

The feedback is rule-based, so it stays aligned with actual test results. Optional LLM evaluation can be used for explanations, but the app still works in mock/local mode.

### Model Type

The model is a scikit-learn `RandomForestRegressor`.

Why RandomForestRegressor:

- handles nonlinear scoring relationships well
- works with mixed numeric/binary features
- does not require huge datasets to be useful
- gives stable results for tabular rubric features
- is easy to train and serialize with joblib

### Training Data

The project does not yet have a large real dataset of human-labeled submissions. Because of that, `train_model.py` generates synthetic training rows aligned with the runtime scoring rubric.

The training script uses the repo-local question bank to calibrate:

- question count
- difficulty distribution
- test case count
- topic diversity

Default training bank:

```text
server/src/data/ai-mock-interviewer-all-unique-questions.json
```

Training generates synthetic examples across these cases:

- perfect submissions
- mostly correct submissions
- partially correct submissions
- zero-test-pass submissions
- starter-template submissions
- explanation-only or explanation-assisted submissions
- different code lengths
- different execution times
- different explanation quality levels

## How to Improve Model Accuracy

The current ML model is accurate against the synthetic rubric it was trained on. To improve real-world accuracy, the next step is to collect real labeled data.

Recommended improvements:

1. Store every real submission as a training row:
   - question id
   - topic
   - difficulty
   - code
   - explanation
   - test results
   - deterministic features
   - final score
   - optional human reviewer score

2. Add human labels:
   - code correctness label
   - code quality label
   - explanation quality label
   - final interview score

3. Train on real outcomes:
   - split by user/session to avoid leakage
   - use train/validation/test sets
   - track MAE by score range and topic
   - compare model predictions to human labels

4. Add question-level features:
   - topic one-hot encoding
   - difficulty
   - number of hidden tests
   - expected complexity class
   - harness type

5. Improve code quality features:
   - AST complexity for all languages
   - cyclomatic complexity
   - duplicated code detection
   - bad-pattern detection
   - memory usage when available

6. Improve explanation features:
   - semantic similarity to solution approach
   - LLM-generated rubric labels
   - explicit edge case coverage
   - complexity explanation detection

7. Use stronger models once real data exists:
   - GradientBoostingRegressor
   - XGBoost or LightGBM
   - calibrated ensemble of deterministic score + ML score
   - separate models for correctness, code quality, and explanation quality

8. Keep hard correctness rules:
   - all tests pass should stay near 100
   - no meaningful code should stay near 0
   - zero tests passed should not receive high score because of explanation alone unless it is an explanation-only question

## Troubleshooting

### Frontend cannot reach backend

Check that backend is running on port `5001`:

```bash
Invoke-RestMethod http://localhost:5001/api/v1/health
```

The Vite dev server proxies `/api` requests to the backend.

### Code always fails test cases

Check Piston:

```bash
docker ps
Invoke-RestMethod http://localhost:2000/api/v2/runtimes
```

Also confirm the question has valid `testCases` and the right `testHarness`.

### ML is not used

Check:

```bash
Invoke-RestMethod http://localhost:8000/health
```

If `modelLoaded` is false, train the model and rebuild the ML Docker service.

### Database has old question count

Re-import the repo-local bank:

```bash
npm run import:questions --workspace=server -- --replace
```

### Perfect code does not score correctly

Run:

```bash
python ml_service/verify_perfect_score.py
```

Also check that the backend has real test execution results. A perfect score depends on all test cases passing with meaningful code.
